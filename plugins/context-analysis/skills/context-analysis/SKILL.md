# Context Analysis

## Overview

`/context` tells you WHICH category is heavy. This skill tells you WHICH SPECIFIC tool or memory to cut, whether cutting it is even possible from local config, and which reload mechanism (if any) actually applies the change. Cutting the wrong tier's config silently does nothing — verify before declaring victory.

## When to Use

- `/context` shows System tools, MCP tools, or Memory files as a large or unexpectedly growing line item.
- Before adding a new MCP server or plugin — check its tool count and whether it supports scoped filtering.
- A settings.json edit to cut context doesn't seem to have worked after `/reload-plugins`.
- User asks: "what can we cut", "why is context so full", "find redundant MCPs", "reduce token usage".

## Complementary Tool: rtk

This skill trims tool/memory *schemas* — a different token cost from raw Bash command *output* (git diffs, test logs, build output), which is often the larger share of a session's tokens on repetitive dev commands. `rtk` ("Rust Token Killer") is a CLI proxy that rewrites common commands (git, grep, etc.) through a filtered/summarized path via a Claude Code `PreToolUse` hook, aiming for large savings there. (Not an Anthropic tool — check with whoever maintains it internally for install instructions if it's not already on your machine.)

If it's installed, **verify the hook is actually active before recommending it — installed and active are not the same thing.** `rtk gain` prints `No hook installed — run 'rtk init -g'` when the hook was never wired up, and can show 0% savings even with dozens of logged commands if every one of them was `rtk proxy <cmd>` (an explicit manual bypass) rather than the real automatic filtering path — that's a strong sign the hook isn't installed, not that rtk doesn't work. Confirm both: `rtk gain` shows no "no hook" warning, and `~/.claude/settings.json`'s `hooks.PreToolUse` actually contains an `rtk hook claude` entry (`rtk init -g` sets this up, but doesn't always patch `settings.json` automatically in non-interactive contexts — check and add it by hand if needed, then restart the session).

**If it's active, review its actual impact periodically, not just once at install time.** `rtk gain` / `rtk gain --history` give the headline numbers (commands routed through it, tokens saved, savings %) — but that aggregate doesn't surface the failure mode that matters most: rtk's filtering being *wrong* for a given command, forcing the agent to redo the work. Look for a second, qualitative signal: past assistant messages where the model itself pushed back on rtk's output — phrases like "the output was truncated", "let me get the raw/full output instead", "re-running without rtk", "rtk cut off/missed X". That's evidence of a real wasted round-trip that the token-savings aggregate would never flag on its own.

This second check means grepping potentially dozens-to-hundreds of transcript files for a pattern, then reading enough surrounding context in each hit to judge whether it's a genuine complaint versus an unrelated mention of "rtk" — a bulky, mechanical, classification-shaped task, not a reasoning-heavy one. **Delegate it to a subagent on a cheaper model (e.g. `model: "haiku"` on the `Agent` tool) rather than doing it inline or reading transcripts yourself.** Narrow the dispatch to keep it cheap and reliable: have the subagent (1) `grep -l` for `rtk` across transcripts to shortlist candidate files first — don't hand it the full transcript corpus, (2) for each candidate, classify the surrounding message as complaint/non-complaint and return only a compact digest (file, quote, verdict) rather than raw excerpts. Classifying existing text like this plays to a cheap model's strengths; it's a different task shape from asking Haiku to transcribe or rewrite code (which it's known to botch) — this is read-and-tag, not generate.

## The Levers, and How Each Is Actually Cut

**Update (2026-07-25):** `permissions.deny` with a **bare tool name (or bare-name glob)** now removes the schema from context for *any* tool — built-in **and MCP** — per the current official docs (code.claude.com/docs/en/permissions): "Deny rules... `Bash` removes tool from Claude's context so Claude never sees it... a bare-name glob deny rule is removed from Claude's context, the same as a bare tool name." This supersedes the older, buggy behavior documented in anthropics/claude-code#6699, #6631, #27040 (deny rules silently ignored / execution-only). It means per-tool MCP trimming no longer requires the target server to support its own toolset/whitelist headers (GitHub, Datadog) — you can hard-deny individual `mcp__server__tool` names, or a whole server via `mcp__server__*`, directly in `settings.json`, on any MCP server, whitelist support or not.

This is a **hard deny**, not a soft "ask": the tool becomes fully uncallable until you remove the rule — there's no per-call override. **Confirmed** (2026-07-25, via `context_snapshot.sh` — see step 2 — run immediately after a `settings.json` edit): a freshly-started session, including a headless one, reflects bare-name MCP denies with no restart of anything beyond starting that new process. What's still unconfirmed is whether the same denies also apply *live*, mid-session, without starting any new process — don't assume that without testing it directly.

| Source | What it is | How to cut it | Reload needed |
|---|---|---|---|
| **Any tool, built-in or MCP** | Whatever's already connected/loaded, at the individual-tool granularity | `permissions.deny: ["ToolName"]` or `["mcp__server__tool"]` or `["mcp__server__*"]` — bare name/glob only; a *scoped* rule like `Bash(rm *)` or `Tool(param:value)` leaves the schema in context and only blocks matching calls | **None** for built-in tools — confirmed empirically (denying `Artifact`/`DesignSync`/`LSP` dropped `/context all`'s System tools total on the very next turn, same session). For MCP tools, confirmed in any freshly-started session (a full restart, or a headless `claude -p "/context all"` run right after the edit — see step 8); whether it also applies live mid-session without starting anything new is still unconfirmed |
| **MCP servers — local** | Registered directly in `~/.claude.json` under `mcpServers` | Edit/remove the entry | **Full restart** — the connection is established once at session start; `/reload-plugins` explicitly does not touch this file |
| **MCP servers — plugin-hosted** | Provided by a plugin, visible in `settings.json` → `enabledPlugins` | `"<plugin>@<marketplace>": false` in `enabledPlugins`, or the plugin's own scoped-filtering mechanism if it has one (e.g. Datadog toolset env var, GitHub's hosted MCP `X-MCP-Toolsets`/`X-MCP-Exclude-Tools` headers) | `/reload-plugins --force` is enough |
| **MCP servers — claude.ai cloud connector** | Tool names literally prefixed `mcp__claude_ai_*`. Not in any local file — auto-fetched from your claude.ai account at session start | `disableClaudeAiConnectors: true` in settings.json kills ALL of them at once (no per-server local switch exists); otherwise disconnect individually in claude.ai's own connector settings | **Full restart** — `/reload-plugins` does not fetch/re-fetch these at all |

**Practical implication:** the bare-name deny row is now the default lever for trimming individual unused MCP tools — many project-tracker/CRM/docs-style servers ship dozens of tools across feature areas you may never touch (e.g. release-tracking, admin/label-management, a secondary review UI), with no server-side whitelist support. Reach for the server-tier rows only when you want to cut a *whole server* (redundant/unused entirely) or a server's own filtering is more convenient for a large coarse category.

**The failure mode this table prevents:** editing `~/.claude.json` and running `/reload-plugins`, then being confused why nothing changed — that command only reloads the plugin tier. The bottom three rows need a full restart, not `/reload-plugins`.

## Workflow

1. **Scope the cleanup with the user before touching anything, and track each area as its own task.** This skill spans several largely-independent areas — MCP tool/server trimming, memory-file staleness/usage, built-in-tool/system-prompt trimming, plugin toggling, naming/link hygiene — and a full pass is a long, multi-round conversation: each area tends to need its own back-and-forth (per-category keep/deny decisions for one MCP server alone can take several `AskUserQuestion` rounds; a memory audit can surface half a dozen individually-discussable stale entries). Don't silently start auditing everything at once. Ask the user which area(s) they want in scope with an `AskUserQuestion` using **`multiSelect: true`** and one option per area — e.g. "MCP tools", "Memory files", "Built-in tools / system prompt" — not a single bundled "everything" choice forced to compete with the individual areas as mutually-exclusive options; a user who wants two of three areas shouldn't have to either under- or over-select. Then `TaskCreate` one task per area the user selected (e.g. "Audit MCP tool usage: <server name>", "Audit memory staleness/usage", "Naming/link hygiene pass") so progress persists and is visible across the conversation. Mark each `in_progress` when you start it and `completed` only when its findings are actually resolved (fixed, explicitly kept, or explicitly deferred) — don't let one area's cleanup quietly swallow the whole session, and don't leave a started area half-finished when the conversation moves on to something else without noting it as still-open.

2. **Get the picture and snapshot it as the baseline:** you need `/context all`, not the bare `/context` — the `all` argument breaks the category rollups down to per-tool, per-skill, and per-memory-file token costs, which is what lets step 8 diff at the individual-tool level ("`mcp__<server>__<tool>`: 176 tokens, gone") instead of only a coarse category delta. `/context` is a slash command intercepted client-side, not a tool you can invoke on the current session directly — but you're not stuck asking the user to paste it. Run `bash context_snapshot.sh [directory]` instead: it shells out to `claude -p "/context all" --verbose --output-format json` and prints the same markdown report `/context all` shows interactively.

   This spins up a **fresh, separate session** in the target directory (which determines which memory dir and project-level settings get loaded). `total_cost_usd`/`duration_api_ms` come back `0` — it's a local computation, no model call, safe to run as often as you like. Record the full breakdown verbatim — this is the "before" side of the before/after you'll report in step 8.

   **Caveat:** a fresh headless session can have a different connected-server set than the user's *live* interactive session (e.g. it may pick up MCP servers that weren't connected when their session started, or vice versa) — so treat a headless "before" as comparable to a headless "after" of the *same* change, not necessarily to the live session's own `/context` reading. If you need the exact live session's numbers (not a fresh one), you do still need to ask the user to run `/context all` themselves and paste the result.

3. **For MCP tools:** run `classify_mcp_servers.py` (no args needed — it cross-references `~/.claude.json` against every `mcp__` tool call in your transcript history). It tells you the tier, the fix, and whether the server was ever actually used. Zero-use + expensive = cut candidate; but a rarely-used server for a rare-but-critical workflow (incident response, etc.) is evidence, not proof — confirm with the user.

   Redundancy check while you're there: the same capability sometimes exists on two tiers at once — a plugin-hosted MCP server AND a claude.ai cloud connector for the same product (tool names literally prefixed `mcp__claude_ai_<Product>`), coexisting and both connected. That's close to a guaranteed cut on one of the two.

4. **For a specific server's tool-level detail**, or for a **built-in tool** you suspect is unused: `tool_usage.py <name-or-substring>`. Works identically for `mcp__github__` (all tools on that server) or `Workflow` (one built-in tool, exact name). It only reports tools that were *called* at least once — to see the zero-call tools by name, diff its output against the server's full tool list (from `/context all`'s per-tool MCP breakdown, or the server's docs). Zero real calls across many transcripts is a strong signal — cross-check *why* before cutting: is it genuinely unneeded, or is the tool actually broken/misconfigured (e.g. an LSP tool with zero calls despite its backing plugin being enabled — that's as likely to mean "silently not wired up" as "not needed")?

   **Once you have the zero-call list, prefer per-tool bare-name `permissions.deny`** (see the table above) over waiting on server-tier toggles — it works regardless of whether the server itself supports scoped filtering. Group the candidates by feature area/category (e.g. a project-tracker MCP's release-tracking, initiative-management, and doc-editing tool clusters, if those aren't part of your workflow) rather than asking tool-by-tool.

5. **When presenting cut candidates for a decision — MCP tools, servers, plugins, or memories alike — use `AskUserQuestion` with facts, not a bare yes/no.** A category like "should we deny these 7 release-tracking tools?" is a worse question than one that lets the user actually weigh it. For each category/candidate, give:
   - **The concrete stat** — call count and/or age ("0 calls across 156 transcripts", "34 days since last edit, never re-read"), not just "unused."
   - **A one-line explanation of what it does** — assume the user doesn't have the tool's full description memorized.
   - **A concrete example of when it'd be used** — e.g. for a release-notes tool: "asking the tracker 'what's in release v2.3's notes'" — so a "keep" answer is an informed bet on future need, not a guess.
   - **A recommendation with reasoning**, as the first/default option — but let the user override it; zero-use is evidence, not proof, especially for rare-but-critical workflows (incident response, destructive-but-occasionally-useful tools, etc.).

   Batch up to 4 categories per `AskUserQuestion` call and make additional calls for more — don't try to cram ten categories into one question's options. This applies symmetrically to memory-file decisions in step 7: "delete outright" vs. "trim to the durable part" vs. "keep" is exactly the same shape of decision as an MCP tool's keep/deny/ask, and deserves the same fact-first treatment.

6. **Keep script output out of the conversation, not just out of the tool call.** `classify_mcp_servers.py`, `tool_usage.py`, `memory_staleness.py`, and `memory_usage.py` can all produce long listings on a repo with many transcripts or many memory files — dumping the full raw output into every response defeats the purpose of a *context*-trimming skill. Redirect full output to a scratch file (`> /tmp/.../scan.txt` or similar) and only pull the slice you need back into the conversation: the flagged/zero-call rows, a count, a top-N. Summarize categories and counts in prose; don't paste tables of dozens of tool names when "41 of 57 tools on one server, grouped into 9 categories" conveys the same information in far fewer tokens.

7. **For memory files, check two independent vectors, not just one:**
   - **Age** (`memory_staleness.py`, no args needed): flags `project` memories >14 days and `reference` memories >60 days as revisit candidates, based on file mtime. This only tells you the memory hasn't been *edited* — not whether it's still being *used*.
   - **Actual recall** (`memory_usage.py`, no args needed): MEMORY.md's index is always loaded, but an individual memory file only enters context when the model Reads it. This script counts real `Read` tool calls against each memory file across this project's transcripts, so it tells you which memories are genuinely never being pulled back in — a stronger signal than age alone, and one that catches memories that look fine by age (e.g. a `feedback` memory, which age-staleness doesn't flag at all) but that the model has silently never found reason to re-open.
   - Cross-reference both before acting: old + never-re-read is a strong prune candidate; old + still frequently read is not, regardless of age; young + never-re-read may mean the memory's `description` field doesn't match how it'd actually get surfaced.
   - **Never auto-delete** either way — a flag means "worth checking," not "wrong." For each flagged `project` memory, actually verify it against the issue-tracker ticket/PR it names (status, merge state) — don't just eyeball the age. A memory can be *factually wrong*, not just old (the design it describes pivoted after the memory was written — e.g. a planned integration approach that got replaced by a different one before shipping) — that's a stronger signal to rewrite/remove than age alone, and worth calling out distinctly from "just stale." For reference memories, check the path/tool/command still exists. For a "never re-read" `feedback`/`user` memory, ask the user whether the guidance is still standing before removing it — durable memory types are exempt from the age check specifically because they're not expected to need frequent edits, so recall count is their more relevant signal. Use step 5's fact-first `AskUserQuestion` pattern for the keep/trim/delete decision on each one.
   - While you're in a memory file, sanity-check its `[[wiki-links]]` against the actual `name:` frontmatter of the file they claim to reference (not just the filename) — a typo'd or stale link (missing a prefix, referencing an old name) silently breaks the cross-reference with no error anywhere.

8. **Apply the fix per the table above**, then **get the "after" reading from a new or reloaded session, not the current one.** The current session's `/context` reflects the tool/config state that was loaded when *this* session started (or last `/reload-plugins`) — running `/context all` again in the same still-running session doesn't re-derive that from scratch, so it's not a valid "after" measurement regardless of which lever you used. For plugin-tier server changes, `/reload-plugins --force` is enough. For local/claude_ai-tier changes, and for bare-name `permissions.deny` on MCP tools, use a genuinely new session — `context_snapshot.sh` (step 2) is the easiest way to get one, or a full interactive restart if you need the user's own session refreshed. **Bare-name `permissions.deny` on MCP tools is now confirmed** (not just expected) to apply in any freshly-started session, including a headless one spun up immediately after the `settings.json` edit — verified by denying a batch of tools and finding exactly the expected survivors in the next `context_snapshot.sh` run, no restart of anything required beyond starting that new process. What's still unconfirmed is whether it also applies *live*, mid-session, without starting a new process at all — don't assume that without testing it directly in the session you actually care about. Don't assume a config edit worked just because the file saved cleanly, and don't substitute the pre-change numbers for a real "after."

9. **Report the before/after, not just "done."** Diff the new/reloaded session's `/context all` reading against the step-2 baseline, per tool/category. State the concrete delta — e.g. "MCP tools: 41.8k → 28.3k tokens (-32%), total: 98.2k → 84.7k (-14%)" — rather than a vague "should be smaller now." If the reload/restart hasn't happened yet, say that plainly and present step-8's numbers as pending, not final — the point of this step is evidence, not a victory lap.

## Common Mistakes

- **Assuming per-tool `permissions.deny` requires the MCP server to support its own scoped filtering.** It doesn't (as of 2026-07-25) — a bare tool name or bare-name glob (`mcp__server__tool` or `mcp__server__*`) removes the schema from context regardless of server support, per current docs. This corrects an earlier, now-outdated version of this guidance that assumed MCP deny was execution-only; that was true under a bug documented in anthropics/claude-code#6699/#6631/#27040, not the current behavior.
- **Confusing scoped deny with bare-name deny.** Only a *bare* tool name/glob drops the schema. A scoped rule like `Bash(rm *)` or `Tool(param:value)` leaves the tool visible and only blocks matching calls — same tokens spent either way.
- **Running `/reload-plugins` and declaring done for a server-tier change.** It only reloads plugin-hosted MCP servers. Local (`~/.claude.json`) and claude.ai-connector tier changes need a full restart — verify with a fresh `/context all` in the new/reloaded session, not by re-running it in the session you edited from.
- **Assuming whole-server toolset/tool-whitelist *headers* (GitHub's `X-MCP-Toolsets`, Datadog's env var) exist on every MCP server.** They're opt-in per server and still useful for coarse category filtering at connection time, but they're no longer the only way to trim a server without header support — bare-name `permissions.deny` works everywhere now.
- **Trimming a zero-call tool without asking why it's zero.** Could mean genuinely unneeded, or could mean broken/never-wired-up (e.g. an LSP tool with a supposedly-enabled backing plugin that's never actually connecting). Both look identical in the call-count data; only one is safe to walk away from without investigating further.
- **Hard-denying a destructive-but-occasionally-useful tool instead of moving it to `ask`.** A zero-call tool that does something irreversible (delete/merge/resolve) is often better served by `permissions.ask` — visible and confirmable, not silently missing — than a hard `deny`.
- **Deleting a flagged stale memory outright.** `memory_staleness.py`'s flag is "old enough to check," not "confirmed wrong." Always surface the specific claim to the user before removing.
- **Skipping the before/after report.** Without a step-2 baseline reading, "I trimmed some tools" is unverifiable. Always capture `/context all` before changes and after, and state the actual per-category delta.
- **Diving straight into a full audit instead of scoping it first.** This skill covers several independent areas; starting all of them at once without asking, or without a task per area, tends to produce a sprawling conversation where earlier areas' open decisions get lost. Scope with the user and track areas as tasks (step 1) before running any script.
- **Scoping with single-select instead of multi-select.** Forcing a choice between individual areas and one bundled "everything" option makes "MCP tools + memory but not built-in tools" impossible to express in one answer. Use `AskUserQuestion` with `multiSelect: true` and one option per area (step 1) so any combination is a single click.
- **Pasting a script's full raw output into the conversation.** `classify_mcp_servers.py`/`tool_usage.py`/`memory_staleness.py`/`memory_usage.py` output scales with transcript/memory count — redirect to a file and summarize (step 6), don't dump it all into context just because the tool call succeeded.
- **Asking a bare keep/deny question instead of a fact-first one.** "Deny these unused tools?" forces a guess. "0 calls across 156 transcripts; does X (one-line explanation); example use: Y — deny, keep, or ask?" lets the user actually weigh it. Apply this to memory keep/trim/delete decisions too, not just MCP tools (step 5).
- **Asking the user to run `/context all` and paste it back, by default.** `context_snapshot.sh` gets the same reading headlessly, for free, in one Bash call — reserve the ask-the-user path for when you specifically need their *live* session's numbers (step 2's caveat), not as the default first move.
- **Recommending rtk without checking it's actually active.** A binary being installed doesn't mean the `PreToolUse` hook is wired up. Check `rtk gain` for the "no hook" warning and confirm `settings.json` actually has the hook entry before telling someone it'll save them tokens.
- **Scanning transcripts for rtk-frustration signals inline instead of delegating.** Grepping and reading through dozens-to-hundreds of transcript files yourself burns exactly the context this skill exists to protect. Dispatch a cheap-model subagent for the shortlist-then-classify pass instead (see the rtk section) — it's a classification task, not a reasoning one.

## Scripts

- `bash context_snapshot.sh [directory]` — headless `/context all` reading (see step 2) via `claude -p`, no interactive session or user paste required. Local computation, zero cost.
- `classify_mcp_servers.py` — tier + usage + fix, per MCP server, from transcript history + `~/.claude.json`.
- `tool_usage.py <name>` — call counts for one tool or every tool on a server.
- `memory_staleness.py` — age + staleness flags for this project's auto-memory files (vector 1: last edited).
- `memory_usage.py` — real recall counts per memory file, from `Read` tool calls in this project's transcripts (vector 2: last actually used). Cross-reference with `memory_staleness.py` — they measure different things and agreement between the two is a stronger signal than either alone.
- `proxy_log_tools.py --latest <dir>` — byte-exact system prompt and tool schema sizes from a captured API request (requires a logging proxy in front of the Anthropic API; optional, `/context` covers most of this without one).

All six are read-only — they never edit config or delete anything themselves.
